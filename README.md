# Webhook Radar

支持多用户的通知与监控工作台。每个账户独立管理 Webhook、AI 设置、监控规则、自动下单、活动记录和排查日志。概览、智能创建、任务与提醒、快速发送、通知渠道、AI 设置、读取设置、活动与日志、账户安全分别占用独立页面；左侧导航可折叠，手机上可横向滑动切换。页面地址中的锚点可直达相应功能，浏览器前进后退也会切换页面。Docker 镜像包含所需依赖及监控浏览器。

## Docker Compose 部署

安装 Docker 后，在服务器运行一条命令：

```bash
curl -fsSL https://raw.githubusercontent.com/godluo666/webhook/main/install.sh | bash
```

安装脚本会检查 Docker 和 Compose，先尝试拉取 GHCR 中最新的预构建镜像并更新容器；若镜像不可拉取，就从公开仓库自动构建。脚本会临时取得 Compose 配置并在结束时删除，不会遇到远程 Compose 配置的交互确认；无需手动下载文件或执行 `git clone`。**以后升级时重新运行同一条命令即可**，数据卷不会删除。只想从源码构建时，可直接执行：

```bash
docker compose -p webhook-radar -f https://github.com/godluo666/webhook.git#main:compose.build.yaml up -d --build --wait --wait-timeout 90
```

默认仅服务器本机可打开 <http://127.0.0.1:3000>。需要从其他设备访问时，明确开放 3000 端口并重建容器：

```bash
curl -fsSL https://raw.githubusercontent.com/godluo666/webhook/main/install.sh | env RADAR_BIND=0.0.0.0 bash
```

然后打开 `http://服务器IP:3000`。若仍无法连接，请检查服务器防火墙和云平台安全组是否放行 TCP 3000。数据保存在 Docker 命名卷中，重建后仍会保留；更新时再次运行所选的命令即可。对外开放注册时建议设置 `SIGNUP_CODE`。

仓库中的 `compose.yaml` 使用预构建的 GHCR 镜像。镜像包公开后，或服务器已经登录 GHCR 时，可以直接用 Compose 拉取并升级：

```bash
docker compose -p webhook-radar -f https://github.com/godluo666/webhook.git up -d --pull always --wait --wait-timeout 90
```

GitHub 仓库公开与 GHCR 镜像包公开是两项独立设置。镜像包仍为私有时，直接拉取镜像需要先登录有权限的 GitHub 账户；一键脚本会自动改用本机构建。升级时沿用原来的 `RADAR_BIND`、`RADAR_PORT` 等环境变量，以保持访问地址不变。

## 在 1Panel 中更新镜像

镜像地址固定为 `ghcr.io/godluo666/webhook:latest`。`main` 分支每次构建成功都会更新这个标签。1Panel 要从 GHCR 拉取，镜像包必须允许服务器访问：到 GitHub 账户的 **Packages → webhook → Package settings → Change visibility**，设为 **Public**。仅将代码仓库设为公开不会改变镜像包的可见性。公开后先在服务器验证：

```bash
docker pull ghcr.io/godluo666/webhook:latest
```

之前一键安装若回退到 `webhook-radar:local`，请再运行一次上面的一键命令，让现有容器改用 GHCR 镜像；数据仍在 `webhook-radar_radar_data` 卷中。之后在 1Panel 的**容器列表**选中 `webhook-radar` 对应的容器，使用容器的**升级／更新镜像**操作，拉取 `latest` 并重建容器。只在**镜像列表**点“拉取”不会更新已经运行的容器。若要由 1Panel 管理整个编排，可以将仓库的 `compose.yaml` 粘贴到 1Panel 新建编排的编辑器中；请在编排变量中设置 `RADAR_BIND=0.0.0.0`，沿用相同的数据卷，先停止旧容器以免 3000 端口冲突。

## 启动

需要 Node.js 20.18.1 或更新版本，建议使用 Node.js 24。

```bash
npm ci --ignore-scripts
node server.js
```

打开 <http://127.0.0.1:3000>，注册账户后使用。`PORT` 可设置端口，`HOST` 可设置监听地址；默认只监听本机。进程需要持续运行，监控任务才会按间隔检查。设置和数据保存在 `.data/state.json`。

直接运行 Node 时，`.env` 不会自动加载。若把邮件参数写入 `.env`，请使用 `node --env-file=.env server.js` 启动；Docker Compose 则会读取同目录的 `.env`。

可选环境变量：

| 变量 | 用途 |
| --- | --- |
| `DATA_DIR` | 数据目录，默认项目内 `.data` |
| `SIGNUP_CODE` | 设置后，新用户注册必须填写此邀请码 |
| `COOKIE_SECURE=1` | 经 HTTPS 访问时，为登录 Cookie 加上 Secure 标志 |
| `RESEND_API_KEY` | 邮箱验证码发信服务的 API Key |
| `MAIL_FROM` | 发件地址，须属于已在 Resend 验证的域名 |
| `HTTP_PROXY` / `HTTPS_PROXY` | Node.js 24.14+ 会自动使用代理，并跳过本地地址；较旧版本请通过运行环境配置网络 |
| `MONITOR_BROWSER_EXECUTABLE` | 直接运行 Node 时指定 Chrome / Chromium 可执行文件，Docker 已内置 |
| `MONITOR_BROWSER_ENABLED=0` | 关闭浏览器读取，默认启用 |
| `MONITOR_SS_EXECUTABLE` | 直接运行 Node 时指定 shadowsocks-rust 的 `sslocal` 可执行文件，需支持 HTTP 本地代理；Docker 已内置，无需额外配置 |
| `MONITOR_PROXY_TEST_URL` | 可选的代理出网检测地址，应返回 JSON `{ "ip": "出口IP" }`、纯 IP 或 Cloudflare trace；不配置时使用内置检测服务及备用服务 |
| `MONITOR_BROWSER_HEADLESS=1` | Linux 上使用无界面浏览器，默认在 Xvfb 中运行 |
| `MONITOR_LOG_ROOT` | 可选的日志目录根路径；每个账户只读取其中以自身账户 ID 命名的子目录。默认 `.data/monitor-logs` |

只加载 `users` 中的多用户数据；旧版未认领工作区和认领码已移除。现有账户名下的监控和 Webhook 会保留。

邮箱验证码通过 [Resend 邮件 API](https://resend.com/docs/send-with-nodejs) 发送，不需要自建邮局。先在 Resend 验证发件域名，设置 `RESEND_API_KEY` 和 `MAIL_FROM`，例如 `Webhook Radar <notify@example.com>`。两项均配置后，新账户注册必须填写邮箱、接收 6 位验证码并在 10 分钟内验证；已登录用户绑定或更换邮箱也需要当前密码和发往新邮箱的验证码。验证码每 60 秒最多重发一次，每个邮箱每小时最多 5 次，输入错误达到 5 次后失效。服务重启后未使用的验证码失效。

未配置邮件服务时，用户仍可用用户名和密码注册，但不能绑定未经验证的邮箱；页面会明确显示邮件服务尚未启用。注册后会显示一次恢复码，请妥善保存。忘记密码时，用用户名和恢复码设置新密码；恢复成功后恢复码会换新。已登录用户可以修改密码或凭当前密码重新生成恢复码。

## 通知渠道

添加多个 Webhook 地址，逐个测试、停用或删除。支持 Slack、Discord、企业微信、飞书、钉钉和 ntfy，也可以使用通用 JSON Webhook。ntfy.sh 地址可自动识别；自建 ntfy 请手动选择 `ntfy` 格式。每个 ntfy 渠道可设置默认优先级 1–5；手动通知和监控规则可以单独覆盖，留空时使用渠道默认值。优先级仅用于 ntfy。

手动通知和每条监控任务都可以选择接收渠道。部分渠道发送失败时，手动发送会自动选中失败渠道以便重试；监控任务会在下次检查只重试失败渠道。

## 通知内容、预览与模拟

所有监控和日历提醒都可以修改通知标题和正文。创建确认页直接显示通知编辑区；已有任务点击“通知内容与预览”打开侧栏。修改后自动更新接收效果，不调用 AI。修改文案不会重建检测基线或改变提醒时间；已进入重试队列的消息仍使用触发时的内容。

点击“本次详情”“匹配条目”“当前值”等按钮可插入动态内容，也可以用自然语言要求 AI 改写。默认包含实际检测详情：匹配条目名称、逐项状态变化、数值变化、网页匹配附近的文字、日志摘要或订阅新条目。JSON 列表可以配置已知名称字段，未指定时识别常见的 name、model、title、product_name、product_key、id，不再只输出匹配数量。自定义正文按编辑内容发送。监控地址、任务名称、时间均不会在模板外自动追加；需要地址时点击“监控地址”插入 `{{source}}`，也可自己写链接，删除后就不再发送。标题和正文可以分别清空，不会自动恢复默认模板，但不能同时为空。ntfy 空正文会被接收端替换为默认消息，因此应用会提示填写正文；其他渠道可仅发标题，详见 [ntfy 消息格式说明](https://docs.ntfy.sh/publish/#publish-as-json)。升级前排队消息中的独立来源地址也不会再自动追加；原正文中已有的文字仍按触发时保存的内容发送。

预览区分“真实检测数据”“示例数据”和“提醒内容”。创建时试跑会更新真实结果；没有命中或尚未读取来源时使用明确标注的示例。正式触发时动态内容取自当次检测。“查看渠道发送内容”可核对各平台请求正文，ntfy 渠道显示实际采用的优先级。

“发送模拟通知”实际发送当前预览，标题加上 **【模拟】**，用于验收文案和渠道效果。模拟不创建任务，不改变检测快照、连续失败次数、提醒时间或正式通知重试队列。预览凭据仅当前账户可用，10 分钟过期，每次只能发送一次；需要重发时刷新预览。渠道修改后必须重新预览。模拟及正式发送内容会记录在当前账户的日志中。

预览、编辑文案、试跑、模拟发送和定时检测均由本地程序执行；只有自然语言生成、对话调整、用户发起的 AI 修复和 API 连接测试调用配置的 AI 接口。

## 监控来源

在“智能创建”页面直接描述需求，AI 会在需要时追问目标地址或触发条件；回答后生成规则预览，确认后才保存并开始检查。来源可以是 HTTP 地址、`tcp://主机:端口` 或 `log:相对路径`，也可在选填区域单独填写。没有实际来源时不会创建一条无法运行的规则。新库存任务默认每 30 秒检查，价格和网页变化默认每 5 分钟检查；旧任务保留原周期。告警级别默认 warning。创建预览和已有任务的“基本信息”均可按秒、分钟或小时设置周期，例如每 30 秒检查一次。最短 1 秒，与本地调度精度一致，不再限制为 5 分钟或最多 24 小时。保存后按新周期安排后续检测，保留已有检测状态；正在进行的检查会先完成，不并发重叠。定时检查不调用 AI，也不消耗模型额度。AI 输出若漏写必要字段，服务端会自动尝试修正一次。用户可以在同一次创建中询问原因或补充需求；助手会直接回答问题，并避免重复追问。对话只存在于当前页面的创建草稿中，每次请求发送原始需求、页面分析摘要、当前规则草稿和最近 6 条对话；点击“重新开始”、创建成功或退出登录后清空。每次追问仍会调用 API 并消耗相应模型额度，历史排查日志不会作为下次 AI 对话上下文。生成的逻辑可在预览和任务编辑页查看、修改。已有账户名下的任务继续运行。

“立即检查”会马上检查来源。对“当前有货”“页面包含文字”“服务不可用”等状态条件，手动检查时只要条件满足就再次发送；定时检查只在条件从不满足变为满足时发送。对补货、字段变化、新条目和新增日志等变化条件，仍须出现真实的新变化才会通知。

如果网址后面紧跟中文指令，请把网址填入独立的“监控来源地址”输入框，指令框只写监控条件。地址含中文路径时也建议这样填写。预览会显示完整来源 URL；对含糊的地址解析会给出提示。

| 来源 | 指令要点 | 触发方式 |
| --- | --- | --- |
| 网页文字 | 地址和引号内的关键词 | 文字出现或消失 |
| JSON API | 地址、字段路径和比较值 | 条件满足、字段变化或条目状态变化 |
| RSS/Atom | 订阅源地址，可加标题关键词 | 出现匹配的新条目 |
| GitHub Release | 公开仓库的 GitHub 地址 | 最新 Release 的版本号改变 |
| DMIT | “监控 DMIT 补货”或“DMIT 任意有货时通知” | 前者监控状态变化，后者首次有货立即通知 |
| HTTP/TCP 服务 | 健康检查 URL 或 `tcp://127.0.0.1:端口` | 不可用、恢复可用、响应超过阈值 |
| 本地日志文件 | 账户日志目录内的 `log:app.log` 等相对路径 | 新增行包含指定文字 |

日志监控只读取当前账户的日志目录，页面会显示该目录的实际路径。将要监控的文件放在目录内，再填写 `log:文件名`。默认首次检查只记录文件末尾位置，之后仅检查新增行；明确要求检查现有日志时，可在 AI 生成的规则中使用 `initial: "notify"`。单次读取最多 1 MB，文件轮转或截断后会从新文件的末尾部分继续。Docker 内的 `localhost` 指容器本身；要监控宿主机服务或日志，需在部署时提供可访问的地址或将日志挂载到对应账户目录。

DMIT 全量库存使用[第三方公开数据](https://vps.thairath.eu.org/)，购买前请以 [DMIT 官方页面](https://www.dmit.io/pages/pricing)为准。网页监控支持直接请求或浏览器渲染后的 HTML。动态内容可使用浏览器读取，验证失败可配置独立的代理出口。

## AI 自动下单

在 **任务与提醒 → 对应监控 → 自动下单（选填）** 配置，不需要切换到其他页面，也没有选择监控的下拉菜单。每条监控使用独立的下单账户、商品要求、预算和可选 AFF 链接。填写商品链接，再描述规格、计费周期等需求。商品名称或型号可留空由 AI 识别，也可点击 **手动点选商品**，在已登录的商品页面选择名称或购买入口；点选只读取页面，不创建订单。币种从真实结算页面识别，无需填写；试跑展示并绑定识别出的商品、币种、数量及总价，正式执行发现商品或币种变化会停止；没有固定 VMISS 或其他商城结构。监控条件发生满足变化时触发，每份配置执行一次，重复检查不会再次购买。

先填写网站登录页面地址并点击 **打开登录页面**。在同一页的登录画面完成账号、密码和二次认证，再点击 **保存登录会话**；未完成登录时会保留窗口并显示具体原因，不会一直显示正在保存；登录菜单中隐藏的退出链接也可以用于核验。服务器私下保存 Cookie、localStorage、IndexedDB 和 sessionStorage，重启后可以恢复。登录浏览器及代理有十分钟期限；关闭窗口即释放。**验证登录状态** 可提前检查，**清除登录状态** 删除此监控的保存会话。每次试跑和执行都会验证账户，登录失效会停止。会话、密码和输入值不通过工作台 API 回显，也不发送给 AI。登录页面需要能返回当前商家网站并有可验证的退出登录入口；跨站 SSO、无法保存的验证状态会明确报错。

在 AI 设置保存模型与 API 地址后，点击 **生成并试跑**。系统观察真实页面，调用配置的 AI 编写 JavaScript；后续页面与代码不符时，提供实际页面和错误供 AI 修正，最多三次。没有预置商家下单脚本，模型不可用时也不会用模板替代。代码可以在运行时读取 DOM、判断流程和重新选择元素，再把当次核对选择器交给提交执行器。试跑会操作商品配置和购物车、核对真实订单，但不创建订单或付款。启用后，页面结构变化可在提交前自动生成新代码、重新试跑，再执行一次；预算、商品、数量、币种、账户、AFF 和执行范围保持原要求。结构修复最多启动一次，不修复预算或账户校验失败，也不重试已经提交的订单或付款。修改配置、账户或监控条件后需要重新生成、试跑并启用。

正常触发直接执行已生成并确认的代码，不等待 AI。执行使用事先保存的账户会话，避免现场重新登录；复用本次刚读取的商品页面，避免重复 GET；商品、价格、数量和币种并行读取。已有归因 Cookie 立即可验证时不添加固定等待，页面跳转完成后也不额外休眠。检测到变化后启动下单不等待本次通知发送完成。页面与执行记录显示从触发到发起下单的耗时；实际速度仍取决于网络、商家响应、检测周期及是否需要修复代码。

**AFF 链接** 可以留空。填写时先验证账户，再访问指定推广入口，最后进入商品和结算流程。AI 根据实际入口参数、Cookie 名称和订单字段生成归因核对方式；宿主检查推广标识与 Cookie 或订单字段一致，且在真正的订单请求中再次验证该值。试跑显示归因核验，成功订单保留“已随订单发送”的证据。归因无法验证、标识不符、同名 Cookie 冲突或入口不可用时停止在提交前；点击提交时 Cookie 被改写或推广字段丢失，会在请求发往商家之前拦截。此检查证明推广标识随请求发送；实际返佣仍由商家规则、账户资格和归因记录决定，无法保证商家结算佣金。

直接选择 **提交前停止**、**提交订单** 或 **提交并用余额付款**。付款只使用账户余额，需要本次订单返回的同源账单 POST 表单；若先返回成功页面，可以读取该页面唯一关联的新账单。付款前核对账单号、币种、实际总价及可用余额，金额必须与下单前核对结果一致。余额不足、余额无法核实或表单选中了其他支付方式时，不发起付款、不部分扣款、不改用银行卡，状态为 **已下单，等待付款**，保存账单号和可打开的付款页面链接，通知也包含链接。外部支付网站、新增银行卡以及付款阶段需要人工验证的流程会停止并显示原因。付款页只在真实订单创建后核对，试跑不创建账单。订单已创建而付款未完成时保留订单和账单号；提交或付款结果未知时保留记录，请在网站核对，不自动重试。

订单和付款开始前都会持久化记录，重启也不会再次下单或扣款。执行中可以 **停止执行**；已经发出的请求仍需核对商家记录。完成后可以在同一监控下 **新建下单配置**，以前的订单保留供查看。升级到商品与币种自动识别版本时，旧的启用授权会暂停，需要重新生成并试跑确认。AI 代码在限制内存、时间和调用次数的 QuickJS WebAssembly 解释器中运行，仅调用受控浏览器操作，不能读取服务端文件、调用 Node 或直接访问网络。账户登录、AFF、试跑和执行均沿用对应监控的网络出口。

## 网页读取、验证与代理

每个网络监控都能独立指定 HTTP / HTTPS / Shadowsocks 出口，包括统一库存、价格、网页、接口规则及旧版 HTTP/TCP 服务任务。创建前打开 **此任务的网络出口（选填）**，选择账户默认、直接连接或此任务的专用代理；后续在任务卡片点击 **代理出口** 可以直接修改。页面分析、候选验证、元素选择、执行、AI 修改和修复沿用该任务选择，账户代理更新不覆盖独立任务。任务卡片显示当前出口和已验证的出口 IP。只改出口保留检测基线；统一规则更换代理前也会实际测试目标，失败不覆盖原设置。代理凭据只交给后端，不进入模型上下文或公开日志。本地日志和日历提醒没有网络读取，无需代理。

在 **任务 → 编辑监控 → 读取设置** 中选择读取方式：自动（先请求，遇到验证时尝试浏览器）、浏览器（执行页面 JavaScript），或直接请求（只使用 HTTP，适合公开接口）。读取过程和错误代码可在原始日志查看。

真实浏览器也可能因服务器出口 IP 被网站限制。参考 [changedetection.io 的代理配置](https://github.com/dgtlmoon/changedetection.io/wiki/Proxy-configuration)，独立的 **读取设置** 页面支持当前账户的 Shadowsocks 节点或 HTTP / HTTPS 代理及目标网站测试。粘贴 `ss://` 分享链接或 HTTP 代理，点击 **验证并应用**，会先验证代理认证和出网，验证通过后让使用“账户设置”的现有及新建网络监控使用该出口（独立代理和直接连接的任务保持自身选择），无需额外安装客户端或修改 Compose；验证失败保留原代理和监控状态，点击清除可恢复服务器出口。现有检测状态、通知内容和待发送记录保留。HTTP 代理地址格式为 `http://用户名:密码@主机:端口`；特殊字符需 URL 编码。凭据不回显，用于该监控的网页、数据接口和 HTTP/TCP 服务检测；AI、Webhook、邮件和本地日志保留各自的执行方式。每条监控在“读取设置 → 网络出口”中可选择“账户设置”“直接连接”或“独立代理”。选择独立代理后填写这条任务专用的 HTTP / HTTPS / SS 地址并测试；保存前再次验证出网，失败不会覆盖原规则。可以给不同规则使用不同节点。已保存的凭据不回显，留空表示继续使用原独立代理，页面显示节点主机、验证时间和出口 IP。切换账户默认或直接连接后仍保留独立配置，方便以后切回；不会把私有代理地址发送给 AI。容器访问宿主机代理时用 `host.docker.internal:端口`，不要用容器自身的 `127.0.0.1`。

SS 使用镜像内的 [shadowsocks-rust](https://github.com/shadowsocks/shadowsocks-rust) 客户端，支持标准分享链接、旧版 Base64 链接、AES-GCM、ChaCha20-Poly1305 和 AEAD-2022。带 `plugin` 的节点暂不支持直接导入，可使用现有客户端提供的 HTTP 代理。每次网络检测启动独立客户端，使用随机认证的本地监听端口，结束后关闭并清理私有临时配置，最多同时运行 4 个客户端；账户默认代理及每条监控的独立代理分别保存，不回显凭据。仅更新镜像即可获得 SS 支持。

**测试代理** 无需填写目标网站，只通过候选代理读取小型 IP 检测响应，显示出口 IP 和耗时，不保存配置、不调用 AI、不发送通知。导入时会重新验证，避免使用过期的测试结果；检测服务默认使用 [ipify](https://www.ipify.org/)，失败时尝试 Cloudflare trace，每个检测请求限时 8 秒。SS 会完成实际加密转发，不能只靠本地端口打开判断可用。检测日志保留每次尝试、错误链和认证错误，隐藏代理凭据。检测服务不可达时暂不应用，可配置 `MONITOR_PROXY_TEST_URL` 使用自己的检测端点。

**测试目标网站** 是独立操作，用于确认代理是否能读取特定来源，可选择 HTTP 或浏览器。目标地址填错不会阻挡代理验证；目标网站跳盾或拒绝访问会单独报告，不改变已保存代理，也不意味着代理完全不可用。

HTTP 与浏览器使用同一代理出口。浏览器验证 Cookie 按账户、网站和代理隔离，只在内存保留最多一小时，重启后清空；临时浏览器目录在读取后清理。浏览器一次运行一个实例，排队有数量及超时限制。直接请求超时 15 秒，浏览器导航与验证共享 45 秒预算，启动和关闭可能额外耗时。

根据 [Cloudflare 官方响应标记](https://developers.cloudflare.com/cloudflare-challenges/challenge-types/challenge-pages/detect-response/)及验证页特征识别跳盾，即使 HTTP 200 也不会当作真实来源。验证失败保留上一次有效结果、不发库存变化通知，并按 1、2、4、8、15 分钟延迟重试，最长 15 分钟。限流遵守 `Retry-After`（最长一小时）；立即检查可提前重试。只切换读取方式或代理保留基线，修改来源地址或检测条件仍重新建立基线。

日志包含各次读取尝试、HTTP 状态、直接请求的 Cloudflare Ray ID、错误代码及下次重试时间。认证凭据和 Cookie 不进入公开日志。浏览器和代理不能保证通过所有验证；出口被拒绝、需要人工 CAPTCHA 或登录时仍可能失败。代理出网验证通过后，仍建议单独测试目标网站的访问结果。

浏览器读取使用 Playwright。Docker 镜像已包含 Chromium、Xvfb 和中文字体，现有只读 Compose 和数据卷可继续使用。1Panel 更新 `ghcr.io/godluo666/webhook:latest` 即可，无需新增浏览器容器。直接运行 Node 时需安装 Chrome / Chromium，并可用 `MONITOR_BROWSER_EXECUTABLE` 指定可执行文件。

## 定时与循环提醒

直接描述“明天上午 9 点提醒我开会”等需求。AI 会按浏览器时区理解时间；日期、时刻或提醒内容不明确时会追问。创建前可以在预览中核对和修改本地时间、内容与接收渠道。提醒到点后由服务端通过已选 Webhook 发送，不需要监控网址，也不会在创建时立即发送。发送失败的渠道每分钟重试；服务重启后仍会处理未完成且已到期的提醒。默认只发送一次；预览或任务编辑中可改为每隔若干分钟、小时、天或周重复（最长一年），并核对首次发送时间。循环任务本轮发送成功后才安排下一次；失败渠道只重试本轮，不会重复发送到已成功的渠道。服务暂停或离线期间错过的周期不会集中补发，恢复后安排下一个未来周期。可随时暂停、调整间隔或改回一次性提醒。
## 修改已有任务

在“任务与提醒”中展开 **编辑监控 / 编辑提醒**，在 **基本信息、提醒条件、通知、读取设置** 四个独立页签中修改；提醒使用基本信息、提醒内容和通知三个页签。检测条件用日常语言说明；服务响应时间以秒显示。JSON 路径、条目标识、完整筛选逻辑放在默认收起的 **高级设置** 中，普通控件与 JSON 会相互同步。

每个任务都有 **与 AI 修改** 入口。告诉助手想改哪里，或询问现有规则的含义；当前规则会作为本次草稿，无需重新描述全部需求。尚未保存的常用设置也可带入草稿。修改方案会展示与原任务的差异，并提供通知内容预览、试跑和模拟发送；只有点击 **确认更新原任务** 才会保存，保留原任务 ID，不会新建副本。暂停的任务保持暂停。取消修改不会影响原任务。

修改检测方式或来源会重新记录状态，并清除旧条件下待发送的通知；只改文案、检查频率、读取方式或代理会保留检测记录。循环提醒可继续调整时间、间隔和内容。若任务正在检查、发送，或在其他窗口已被修改，更新会被拦下并保留当前草稿，避免覆盖较新的设置。

普通编辑和预览不调用 AI；只有向助手发消息时使用已配置的模型。每次请求仅携带配置草稿、原始需求和最近 6 条对话，不包含任务检测快照或历史日志。确认更新、取消修改、退出登录、刷新页面后，本次对话清空；也可随时点击“清空本次对话”保留草稿继续修改。已有的排查日志仍保留，但不会成为后续 AI 对话的上下文。

## AI 创建监控与提醒

应用没有内置模型或 API Key。自然语言生成需要在当前账户中配置 **OpenAI 兼容 Chat Completions API**；默认基础地址为 `https://api.openai.com/v1`，请求发往 `/chat/completions`。点击“测试 API 连接”会用当前填写或已保存的 Key 发送最小请求，并显示连接结果；点击“生成方案”才会为当前指令调用 AI；每次补充回答会继续调用，模型输出不合规则可能额外调用一次以修正。没有配置 Key 或模型时会明确提示。设置区只显示 Key 是否已配置；可通过独立按钮清除已保存的 Key，服务端不会回显 Key。

AI 会先根据业务描述拟定方案，采用合理默认值并在预览列出假设；不会为了检测周期、阈值等可默认的参数反复盘问。缺少目标地址时可以先返回草稿，填上平时访问的网址后直接试跑或创建，无需再调用 AI。关键业务含义确实无法判断时，才问一个通俗问题。普通监控在真实页面分析后生成候选规则，由正式执行器验证，并展示结果；失败会更换候选或重新分析，最多尝试 3 次。试跑不创建任务、不发送通知。用户确认后，保存前会再次读取验证。

预览与任务编辑提供常用参数控件，原始 JSON 收入“高级规则”。本次对话只保留在当前草稿，向 AI 发送原始需求、当前规则草稿、必要的页面分析摘要和最近 6 条消息；创建、重新开始、退出或刷新页面后清空。

普通监控由 AI 解释目标、推荐实际发现的检测方式，再由程序选择经过测试的候选并保存统一规则。RSS、日志、TCP 和 DMIT 列表等扩展任务继续使用受约束的声明式逻辑。服务端不执行 AI 返回的任意 JavaScript。对于 DMIT，“任意有货”会生成首次满足即通知的条件；“补货”会生成从缺货到有货的逐项状态变化条件。AI 输出若与明确指令冲突，服务端会拒绝创建。

监控来源可在对话中补充；定时提醒无需来源 URL。提供来源地址时，服务端会尝试连接，并在创建页展示 HTTP 状态与内容类型或 TCP/日志的可访问情况；完整响应正文不会发送给 AI；新建普通监控或用户主动修复时，会发送经过限制的商品名称、库存、价格和候选依据摘要。对于只关心 HTTP/TCP 服务是否可用的需求，使用程序执行的可用性检测；需要明确业务含义时，可在对话中补充一个触发例子。除内置的 DMIT 来源信息和由用户提供的 GitHub 仓库地址可换算出的公开 Release API 外，监控仍需要实际来源地址。应用目前不能自行搜索网站或访问需要浏览器登录的内容。API Key 不在设置响应和页面中回显。Key 保存在服务端数据文件中，应限制该文件的访问权限。

## Docker

项目包含 `Dockerfile`、`compose.yaml` 和 `.dockerignore`。默认 Compose 文件直接使用已发布镜像；在含有 `compose.yaml` 的目录运行：

```bash
docker compose up -d
```

默认只发布到宿主机的 `127.0.0.1:3000`，数据保存在 Compose 命名卷 `radar_data`。可复制 `.env.example` 为 `.env` 来设置监听地址、端口、注册邀请码、邮件服务和数据位置；需要从其他设备访问时将 `RADAR_BIND` 设置为 `0.0.0.0`。如需复用当前项目的 `.data/state.json`，设置 `RADAR_DATA_VOLUME=./.data` 后再运行 Compose。Compose 以非 root 用户运行应用，只读挂载容器根文件系统，并将数据目录挂载为可写卷。

要监控宿主机 HTTP/TCP 服务，可将来源写成 `http://host.docker.internal:端口/health` 或 `tcp://host.docker.internal:端口`。Compose 已添加宿主机网关映射；目标服务也必须监听容器可访问的地址。容器内的 `127.0.0.1` 只能访问容器自身。

若使用 `release/webhook-radar-docker-1.0.0.tar.gz` 部署包，在目标机器解压后进入解压目录，可复制 `.env.example` 为 `.env`，再执行上面的 `docker compose up -d`。部署包包含构建上下文，不包含账户数据或 API Key。需要自己构建镜像时，可以运行 `docker build -t webhook-radar:local .`，并把 `compose.yaml` 的 `image` 改为 `webhook-radar:local`。

上传到 GitHub 后，`main` 分支的 “Build and publish container” 工作流会先运行测试，再构建并推送 `ghcr.io/godluo666/webhook:latest`。也可以手动运行该工作流。仓库需要允许 Actions 写入 Packages；镜像发布成功后可从 GHCR 拉取部署。

## 日志与排查

“最近活动”下的日志记录每次 AI 连接测试、规则解析、来源检查和 Webhook 发送的结果、耗时、HTTP 状态和具体错误。新解析日志可展开查看原始指令、发送给 AI 的请求体、AI 回复、地址校验结果；检查失败日志记录网络错误码和响应内容。API Key 会从这些日志中隐藏。每个账户只能查看自己的日志；完整日志可通过登录后的 `/api/logs` 读取，最多保留最近 300 条。旧日志没有保存原始 AI 回复，无法追溯补回。

AI 连接测试通过当前 Radar 服务转发，不需要在浏览器允许外部 API 的 CORS。测试日志保存请求编号、实际接口、模型、请求体、HTTP 状态、原始响应和网络错误码，API Key 已隐藏；测试失败后可点击“查看连接日志”。完整 `/chat/completions/` 地址末尾斜杠也会正常处理。

浏览器的 `Failed to fetch` 表示页面没有拿到 Radar 的响应，需结合反向代理和服务日志排查；它不等于 API Key 无效。页面会显示失败请求的路径和编号。服务端连接外部地址失败则展示 DNS、TLS、连接拒绝或超时等底层原因；非 JSON 的反向代理响应会保留 HTTP 状态以便定位。

## 统一监控规则与验证

本次优化保留原生前端、Node.js HTTP 服务和 JSON 文件存储。新增普通商品库存、价格、网页变化、接口状态任务使用统一 MonitorRule；已有账户、任务、代理、渠道、日志、通知重试和日历提醒继续兼容。旧版 RSS、日志、TCP 和 DMIT 列表等扩展执行方式保留，不自动迁移或删除历史任务。

创建流程为：自然语言理解目标 → 实际读取页面 → 分析真实数据与候选区域 → 程序生成统一规则 → 使用正式执行器测试 → 失败时换候选或浏览器分析，最多 3 次 → 展示预览 → 用户确认 → 保存前再次验证并启用。旧格式模型回答中的普通 HTML、JSON 单值或服务规则也会转换为统一格式，库存和价格不会直接执行模型猜出的关键词或字段。无法验证的规则不会保存；失败修改不会覆盖原任务。

MonitorRule 的固定业务字段为：

| 字段 | 用途 |
| --- | --- |
| id、name、type、url | 原任务标识、名称、监控目标、商品或来源原链接 |
| detection_method | html、dom、api、json、browser |
| target_element | 固定 selector、xpath、text、label 字段，技术内容放在高级设置 |
| extraction_rule | 提取方式、真实 JSON 路径、页面数据块或实际发现的只读接口 |
| condition | 固定 operator、value、from/to、initial、failure_threshold |
| trigger_action、interval、notification | 通知动作、以秒保存的周期、已有通知模板 |
| status、confidence、last_test_result | 任务状态、依据质量评分、测试检查项与真实当前值 |

type 仅使用 webpage_change、product_stock、price_change、api_monitor。kind、label、intervalMinutes 是与现有前后端兼容的固定别名；核心执行以统一规则为准。旧任务可通过 monitor_rule 兼容视图读取，不重写原有配置；AI 修改返回新监控目标时，可在原 ID 上升级为实际验证过的统一规则，保留历史、周期、渠道和通知。未保存草稿的 id 为 null，保存时由服务端生成；修改时 id 和 createdAt 不可覆盖。

库存来源按实际发现的接口、JSON、商品结构化数据、DOM 区域、页面文字、浏览器渲染排序。程序只访问页面明确声明或浏览器实际看到的同站 GET JSON 接口，并实际验证其可以再次读取；不编造库存接口。动态页面自动回退到现有 Chromium。库存未知、字段消失、重复标识、同一型号冲突状态和非单一价格均不能当作正常检测结果。多型号库存通过固定 stock_items 提取方式逐一读取型号标识、名称和状态；任一型号补货均可触发，其他型号仍缺货不会阻止通知。多型号价格仍需选择具体售价区域，不自动混用不同型号的价格。

用户明确指定的价格阈值和检测周期优先于模型建议；模型说“只能5分钟”或返回5分钟，不能覆盖用户要求的30秒。创建说明由实际测试结果生成，不采用模型虚构的当前库存、读取能力或频率限制。明确的目标类型与模型输出不一致时要求模型修正。长页面保留摘要和完整内容哈希，全文尾部的变化及关键词仍参与判断，避免保存整页正文。

可信度是程序按检测依据计算的质量评分，并非模型自报的成功概率。last_test_result 保存页面可访问、目标存在、可提取、条件可判断、目标一致的检查结果，以及当前值、检查时间和规则签名。前端提交的 passed 或 confidence 不能绕过保存前验证。

## 原任务修改、修复、调度与检测记录

已有任务可直接修改监控目标、业务条件、频率和接收渠道；selector、XPath、JSON 路径保存在高级设置。价格“低于300改成低于200”会合并原条件，保留原 URL、检测方式、通知配置、任务 ID、创建时间、暂停状态和历史日志。版本号保护防止过期草稿覆盖其他修改。

检测区域失效时保留上次有效结果，不把读取失败解释成补货。后台从当前页面生成经过测试的修复建议，不自动覆盖。用户打开建议并确认后更新原任务；有 AI 配置时，主动发起的修复先让 AI 根据当前规则与页面证据推荐目标，再由程序验证。后台结构修复分析有 30 分钟冷却，常规定时检查不调用模型。

“直接选择网页元素”支持在创建分析失败时继续操作，也可不配置模型直接创建已验证区域任务。用户点选页面快照中的价格、库存或按钮后，服务端记录原 selector、XPath 和文本，再重新读取来源测试。快照隔离脚本、事件、外链资源和表单动作，按账户隔离，10 分钟失效。动态页面可选择浏览器渲染；登录态、人工验证码或无法访问的来源仍需可读取的数据源。

每个任务保存 next_run_time。调度器使用按时间排序的最小堆，并发上限 16；创建、修改、暂停、恢复、删除和检查完成时更新队列，启动时恢复任务。运行时不再每秒扫描全部任务。10 秒、30 秒、1 分钟、5 分钟、10 分钟提供快捷选择，原有至少 1 秒的自定义周期仍保留。

每次检测日志包含任务 ID、时间、当前值、之前的值、变化、是否触发、业务条件、失败原因和读取诊断。任务中的“检测记录”只显示当前账户该任务的记录。现有日志保留上限仍为每账户 300 条。

新库存、价格默认通知使用具体商品名、状态或价格变化、时间和商品原链接；用户自定义模板继续生效。验证和模拟不会产生正式状态变化通知。

## 多型号库存、云端原文预览与任务卡片

## 创建准确性补强：依据一致性与触发场景验证

## 自定义频率与规则一致性

频率按“用户本次明确要求 → 当前草稿或已有任务 → 类型默认值”解析。默认库存30秒、价格和网页300秒、接口60秒只是未指定时的建议，不能变成最低周期。支持1秒起的自定义值及小数，未增加旧5分钟下限或24小时上限；“每半分钟”“每两分钟”“每小时”“一分十五秒检查一次”“every 1.5 hours”等表达由程序换算。响应耗时阈值、价格及网址中的数字不会被当作检查周期。修改已有草稿时，旧对话中的周期不能覆盖当前设置。

普通需求按固定业务模板编译：

| 需求 | 判断与首次策略 |
| --- | --- |
| 商品库存 / 什么时候补货 | out_of_stock → in_stock，首次记录基线 |
| 任意型号有货就通知 | 每个型号 equals in_stock，首次满足也通知 |
| 库存状态变化 | changed，首次记录基线 |
| 价格变化 / 网页变化 | changed，首次记录基线 |
| 价格低于200 | lt 200，保留当前首次策略 |
| 接口异常 | unavailable，默认连续1次失败，首次记录基线 |
| 服务变慢 | slow，未指定阈值时超过3000毫秒，首次记录基线 |

明确阈值、连续失败次数和当前已编辑条件优先于默认模板。只改周期、名称或通知时，保留未修改的目标、条件、提取方式、来源及文案。页面分析采用固定的 API → JSON → 结构化数据 → DOM → 文本 → 浏览器优先级；模型推荐的候选 ID 不能随意颠倒实际证据顺序，手动选择区域继续生效。规则仍需真实验证和确认保存。
